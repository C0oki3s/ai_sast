# Code Scanning PostgreSQL and ORM plan

## Decision

PostgreSQL is the production system of record for Code Scanning. SQLAlchemy 2.x
is the runtime persistence layer. Psycopg 3 is the PostgreSQL driver. Deployment
DDL is stored as ordered SQL files under
`plaidnox_sast/assets/migrations/postgresql/` and is independently applicable by
an operator or deployment job.

SQLite remains only for isolated unit tests and explicitly local operation.
When `PLAIDNOX_DATABASE_URL` is configured, Context Fabric, security knowledge,
hunt-plan caching, Security IR, and findings all use the ORM layer.

## Ownership

This database boundary stores Code Scanning data only. It has no webhook,
installation-token, pull-request, merge-request, dependency, secret, DAST,
cloud, IaC, license, or IDE tables.

Tables use the `code_scanning_` prefix so a future database can enforce grants,
retention, backup, and migrations independently from other PlaidNox products.

## Data model

```text
codebase
  -> immutable snapshot
       -> source file
       -> stable symbol -> versioned content hash
       -> code/security edges
       -> threat statements
       -> scan run
            -> hunt plan -> hunt task
            -> model invocation -> prompt-cache metric
            -> finding -> evidence
                       -> exact context dependencies

security memory  -> scoped to tenant/codebase
security knowledge -> globally or tenant scoped, source backed
knowledge usage  -> scan/task/knowledge audit link
```

Stable identity and version are separate:

- `symbol_id` is derived from codebase, normalized path, qualified name,
  signature, and disambiguator;
- `content_hash` changes when the symbol implementation changes;
- a snapshot-to-symbol row records the version present in one snapshot.

## Transaction boundaries

1. **Snapshot indexing:** insert immutable snapshot, files, symbols, and edges in
   one transaction. A duplicate `(codebase_id, revision)` is reused.
2. **Task lease:** atomically claim a planned/retryable task with owner and lease
   expiry. Expired leases are reclaimable; completed tasks are immutable.
3. **Finding verification:** persist candidate evidence, verdict, exact context
   dependencies, and model invocation in one transaction.
4. **Knowledge update:** upsert by content hash, preserve source provenance, and
   append usage rather than overwriting audit history.
5. **Scan finalization:** a scan completes only when required tasks reach a
   terminal state and coverage validation passes.

## Tenant isolation

Every tenant-owned root row contains `tenant_id`. Repository methods require a
tenant scope. Production deployment should enable PostgreSQL row-level security
after the service identity and operational model are finalized. Application
checks remain mandatory even with RLS.

Knowledge explicitly marked global is immutable to tenant roles; tenant-derived
knowledge remains tenant scoped.

## Migrations

- Migration files are ordered, immutable after release, and recorded in a
  `code_scanning_schema_migrations` ledger.
- No service starts against an unknown/newer schema version.
- Expansion migrations ship before code that writes new columns; contraction
  happens only after old workers are drained.
- Index creation that can block production uses a separate operational migration
  with an explicit rollout note.
- Restore tests run against a real PostgreSQL container, not an SQLite substitute.

## ORM rules

- SQLAlchemy 2.x typed declarative mappings only.
- Repository interfaces return domain values, not ORM objects outside an active
  unit of work.
- Relationships use explicit loading; no unbounded lazy-load loops.
- JSON stores versioned structured evidence, never fields that require indexed
  filtering or referential integrity.
- UTC-aware timestamps are database generated where possible.
- IDs are generated by the application and safe to expose; database sequences
  are not public identifiers.
- Retry only serialization/deadlock/connection failures that are known safe.
- Database URLs and credentials come from the configured environment variable;
  logs use SQLAlchemy's redacted URL form.

## Object storage boundary

PostgreSQL stores hashes, metadata, normalized evidence, small code slices, and
artifact URIs. Full source snapshots, large SARIF/JSON reports, model traces, and
large reproduction artifacts live in encrypted object storage with tenant-bound
keys and retention. A database row cannot point to an artifact owned by another
tenant.

## Deployment flow

```text
provision PostgreSQL
  -> create least-privilege migrator and runtime roles
  -> apply ordered SQL migrations as migrator
  -> verify recorded schema version
  -> start workers with runtime role
  -> health check database and object storage
  -> run canary snapshot scan
```

## Verification

- migration from an empty PostgreSQL database;
- migration from every supported prior version;
- ORM metadata-to-DDL table/constraint parity test;
- concurrent task leasing and idempotent retry tests;
- tenant-bound repository tests;
- transaction rollback and worker-crash recovery tests;
- backup/restore with evidence and finding dependency integrity;
- query plans for snapshot lookup, affected-symbol traversal, task claims,
  finding history, and knowledge retrieval.
